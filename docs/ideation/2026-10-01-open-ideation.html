Grounding Context

Codebase Context

ApplyTrack already has Firebase authentication, owner-scoped application storage, six statuses, search and filters, date-based follow-ups, mobile cards and an immutable fictional demo. Typed data access and Firestore rules enforce ownership. This document proposes directions; none of the ideas below has been implemented.

The verification report records 37 unit tests, 25 emulator browser tests, 20 hosted browser tests with five emulator-only skips, and 24 direct API privacy checks. Those are recorded results, not tests rerun for this document. Saved-to-Applied date assignment and a late account-A read after switching to account B remain recorded coverage gaps, without an established defect.

The frontend is local and deployment remains deferred. No commit history is available. The project stays independent from the portfolio, with no AI, scraping, email reminders, calendar integrations, uploads, extensions, teams or custom backend in v1. The solutions store has no captured lessons beyond its introductory README.

Official Teal and Huntr documentation establishes workflow organization, activity records and exports as prior art. Linear's project updates provide an analogy for separating lifecycle status from context and freshness. None of these sources establishes an unmet ApplyTrack user need.

Topic Axes

Decomposition skipped — surprise-me mode. The shortlist spans follow-up decisions, recruiter demonstration, portability, progress history and offer decisions.

Top pick: a finite follow-up review. It builds on the tracker's attention queue and makes deliberate waiting a meaningful result of a visit. If the immediate goal is explaining the project to recruiters, the read-only evidence tour is the smaller option.

Direction 1

1. A finite follow-up review

Confidence
75%
Complexity
Medium
Description

Make a visit to ApplyTrack a review that can finish. An application can need an action from you, be waiting on an employer, or have no further pursuit planned. Resolving today's follow-up should preserve that meaning without forcing a new date or changing the hiring stage.

Basis

direct: The record has status, application date, follow-up date and notes, but no explicit next-move responsibility (src/features/applications/types.ts:11–16). The attention queue uses status and dates (src/features/dashboard/utils/statistics.ts:15–28). Existing notes and date edits can already express waiting manually.

Rationale

The opportunity is a clear review workflow, rather than more record fields. It could help a person distinguish work they can do from waiting they have consciously accepted. This need is a hypothesis; the project has no observed usage evidence.

Downsides

Responsibility and review completion can turn a small tracker into a task manager. Dates must not imply a message was sent. The idea earns its place only if it improves decisions beyond the current notes and date controls.

Discussion test

Can someone finish today's review while an application remains Applied, without recording a fictitious contact?

Direction 2

2. A read-only recruiter tour with evidence

Confidence
85%
Complexity
Low
Description

Guide a visitor through a few fictional situations using the existing filters and detail views. Pair a useful product decision with one curated account of failure and recovery, then point to dated verification evidence. Visitors observe and inspect; sample records remain unchanged.

Basis

direct: The demo already shares dashboard/list behavior and presents read-only fictional details (src/features/demo/DemoDashboard.tsx:24–29, 52–54, 66–82). UI_UX.md:325–346 defines its read-only boundary. docs/verification.md records the reproduced create/readback problem and its passing regression.

Rationale

Your original goal is a resume project you can explain. This makes existing product choices and measured engineering work easier to inspect without an account. A curated failure story could make the demo memorable, but no recruiter response has been measured.

Downsides

An overlong tour could obstruct the tracker demo. Fictional illustrations must be labeled and must not masquerade as live failures. Evidence becomes stale if claims are not kept dated. Technical detail belongs in the reviewer explanation, away from ordinary tracker flows.

Discussion test

Can a visitor describe one user problem and one tested engineering choice after a short inspection, without signup?

Direction 3

3. A portable application handoff

Confidence
75%
Complexity
Low
Description

Give the owner a readable download of application facts and personal notes, useful when returning after a pause or keeping a copy outside ApplyTrack. Submission context and closure reasons can remain ordinary user-written notes. This direction does not promise imports, restoration, or public sharing.

Basis

direct: Owner-scoped reads already return the application fields (src/features/applications/api/applications.ts:19–43; src/features/applications/types.ts:5–17). reasoned: Context becomes more durable when it remains understandable without the original interface. Export is established prior art in the official Teal and Huntr documentation.

Rationale

The new capability is taking the existing record with you; structured note templates alone would add little. It also offers an interview discussion about preserving date meaning and private ownership at a data boundary.

Downsides

A downloaded file contains private information and is no longer protected by Firestore rules. Format and completeness matter. A readable copy must not be called a restorable backup, and export is useful rather than novel.

Discussion test

Could future you understand what was applied for, what was waiting, and why a record closed without opening this app?

Direction 4

4. A truthful progress notebook

Confidence
70%
Complexity
High
Description

Keep actual stage changes distinct from administrative edits, so a corrected job URL does not imply new hiring progress. A returning user could see what genuinely changed since their last review. Earlier events remain unknown unless the owner supplies them; this direction must not invent historical transitions.

Basis

direct: Both ordinary updates and status changes write updated_at (src/features/applications/api/applications.ts:104–107, 143–151). The model stores only current stage and generic timestamps (src/features/applications/types.ts:11–16). Those facts cannot reconstruct a stage history.

Rationale

One accurately recorded event could support recall, progress review and future explanations. The value is honest history, rather than a chart made from current status counts. Dated activities are already category prior art.

Downsides

This is the largest extension: event meaning, correction behavior, ownership rules and review persistence all need decisions. It could consume the focused v1 budget. Treat it as a later option unless real use demonstrates a need for history.

Discussion test

Can the product distinguish yesterday's interview confirmation from yesterday's spelling correction using recorded facts?

Direction 5

5. Offer received, decision still pending

Confidence
60%
Complexity
Medium
Description

Explore a small personal decision space for an undecided offer: what needs an answer and when the owner wants to decide. Receiving an offer ends some outreach, while a response or question may still need attention. This is a proposed change in product meaning, not a defect in the current implementation.

Basis

direct: src/features/dashboard/utils/statistics.ts:19 excludes Offer alongside Rejected and Withdrawn. UI_UX.md:238–242 intentionally treats those stages as completed. reasoned: Completion of outreach and completion of a personal decision are separate events.

Rationale

This could keep the tracker useful when an applicant has a consequential choice, without notifications or a calendar. Demand is unobserved, and the current completion policy is deliberate.

Downsides

It requires revisiting the documented completed-state policy. It can easily expand into an offer comparison or negotiation product. A response decision should not silently revive old outreach follow-ups.

Discussion test

Should an undecided offer with a tomorrow response date disappear from the attention view?
